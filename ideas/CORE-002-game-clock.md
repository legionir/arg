# CORE-002: حلقه زمان و چرخه به‌روزرسانی شبیه‌سازی

- دسته اصلی: Architecture / Structure
- برچسب تخصصی: CORE, ARCH, PERF
- وضعیت: implemented (اکتبر ۲۰۲۶ — دامنه کامل؛ testing: ‏C-CLOCK-2/3 پاس زنده، C-CLOCK-4 پین‌تست مانده)
- اندازه: M
- ارزش / اولویت: زیاد — زیرساخت همه سیستم‌ها؛ بدون آن اقتصاد و حرکت رفتار قطعی ندارند
- برجسته ★: بله — تصمیم آن قفل معماری است (جدایی منطق از رندر)
> برش اول (اکتبر ۲۰۲۶): حلقه ۱۰Hz + pause + سرعت ۱/۲/۴ + سقف جبران، تست‌شده (تیک مستقل از فریم‌ریت).

## وضعیت فعلی
هیچ tick loop وجود ندارد. هیچ قرارداد به‌روزرسانی (ترتیب تولید → مصرف → حرکت → نبرد) تعریف نشده.

## مسئله / فرصت
بدون ساعت مرکزی: سرعت بازی به فریم‌ریت گره می‌خورد، ترتیب به‌روزرسانی نامشخص می‌شود (تولید قبل از مصرف یا بعد؟) و تست قطعی رفتار غیرممکن است.

## تغییر پیشنهادی
حلقه منطق با گام ثابت (پیشنهاد اولیه: ۱۰ تیک بر ثانیه) مستقل از `requestAnimationFrame` رندر؛ صف به‌روزرسانی با ترتیب ثبت‌شده؛ امکان pause و speed (۱x/۲x) از ابتدا در طراحی لحاظ شود.

## نتیجه مورد انتظار
اجرای یک سناریوی ۶۰ ثانیه‌ای روی دو مرورگر/فریم‌ریت متفاوت، وضعیت منطقی یکسان تولید کند (قطعیت منطق).

## رفتار مورد انتظار
- توقف (pause) پیشرفت منطق را متوقف کند ولی رندر ادامه یابد.
- هر تیک ترتیب ثابتی داشته باشد: تولید منابع → مصرف → حرکت → نبرد (ترتیب نهایی قابل بازنگری ولی ثابت).
- عقب‌ماندگی فریم باعث جهش منطق نشود (clamp تعداد تیک جبرانی).

## وابستگی‌ها
- نیاز دارد: هیچ‌کدام (نقطه شروع است).
- اثر می‌گذارد بر: همه — `ECON-001`، `CORE-001`، `MIL-001`، انیمیشن، `PERSIST-001` (تیک جاری باید ذخیره شود).

## فرضیات / مجهولات
- ترتیب دقیق به‌روزرسانی بازی مرجع نامشخص است؛ فعلاً تصمیم طراحی وب ثبت می‌شود، نه ادعای وفاداری.
- فرکانس بهینه تیک برای مرورگرهای ضعیف نیاز به اندازه‌گیری دارد.

## اولین گام پیشنهادی
- پروتوتایپ ۵۰ خطی: شمارنده تیک + لاگ ترتیب سیستم‌ها + تست قطعیت (دو اجرای ۶۰۰ تیکی با seed ثابت).
